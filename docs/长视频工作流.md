# 可插拔长视频工作流

## 1. 项目与 run

```text
projects/{id}_书名/
├── project.json                 # provider 唯一事实源
├── input/
│   ├── topic_request.md
│   ├── topic.json
│   ├── copy.json
│   ├── script.txt
│   ├── storyboard.json
│   └── candidates/{run_id}/     # 模型候选
├── workflow/runs/{run_id}/
│   ├── state.json               # provider 快照 + 阶段状态
│   ├── tasks/                   # Codex/Antigravity 交互任务包
│   └── image_tasks.json         # 临时、provider-neutral 图片任务
├── assets/scenes/
├── audio/voice/
└── output/
```

新项目先固定两类生成方式：

```bash
PY=/Users/spring/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3
$PY pipeline/workflow.py create --project 003 --llm codex --image imagegen
$PY pipeline/workflow.py init --project 003
```

每个新项目必须显式、独立选择内容生成方式和图片生成方式。
CLI 值与用户可见含义如下：

| 配置 | 值 | 实际执行方式 |
| --- | --- | --- |
| `--llm` | `codex` | Codex 当前会话 |
| `--llm` | `deepseek` | DeepSeek API |
| `--llm` | `antigravity` | Antigravity 当前会话 |
| `--image` | `imagegen` | Codex 内置 ImageGen |
| `--image` | `wanxiang` | 万相 API |
| `--image` | `antigravity` | Antigravity 内置生图 |

Agent 运行环境与生成方式是两个层次。例如 `--llm antigravity --image imagegen`
时，内容阶段由 Antigravity 当前会话写候选；图片阶段在同一 run 进入
`awaiting_external` 后，需切换到 Codex 由内置 ImageGen 逐张执行。工作流不会
自动启动或跨平台调用另一个 Agent。

两项选择及其 model 配置永久固定，完成后也不能通过 `create` 切换；
新项目不继承上一个项目的选择。

已有项目相同配置可重复 `create`，省略参数会保留已有 provider、模型、音色及模板，不重置默认值。要使用另一 LLM、图片模式或模型应新建项目 id。`init` 会核对所有历史 run 的 LLM 与图片配置，并为新 run 保存完整快照；已有 run 始终使用自己的快照。新 ID 不能直接 `init`，必须先 `create`。

## 2. 内容阶段

每一阶段都遵循同一循环：

```bash
$PY pipeline/workflow.py run <run_id> <topic|copy|script|storyboard>
$PY pipeline/workflow.py verify <run_id> <stage>
# 人工明确确认后：
$PY pipeline/workflow.py promote <run_id> <stage>
```

topic 需要先选择候选：

```bash
$PY pipeline/workflow.py select-topic <run_id> <candidate_id>
```

topic 提升时写正式 `topic.json`、更新书名/作者，并将 `{id}_新项目` 安全重命名为 `{id}_书名`。id 不变。

Codex 和 Antigravity provider 都不调用模型 API。`run` 会把上下文、契约和候选目标写入 `workflow/runs/{run_id}/tasks/{stage}.json`，状态变为 `awaiting_external`。对应平台的 `video-maker-production` skill 读取任务包、只写指定候选路径，然后执行统一 `verify`。Antigravity 使用当前会话选中的模型；DeepSeek provider 直接调用 API 并写同一候选格式。

## 3. 图片阶段

正式 `storyboard.json` 只描述叙事语义。新项目默认使用
`visual_style.phase_transition: "direct"`：五个 `PHASE` 仅用于内部结构，
不生成标题图、不占渲染时长，前后内容镜头直接衔接。旧项目未设置该项时保持阶段图兼容。

公共层把视觉风格、角色身份锚点、16:9、字幕安全区和文字策略装配成临时 ImageTask：

```bash
$PY pipeline/workflow.py run <run_id> images
$PY pipeline/workflow.py verify <run_id> images
# 人工查看全部候选后：
$PY pipeline/workflow.py promote <run_id> images
```

ImageGen 与 Antigravity 进入 `awaiting_external`，对应 skill 按 `image_tasks.json` 的密封请求逐张生成 PNG 到候选目录；只有上一张通过完整解码与 16:9 检查后才签发下一张。万相直接调用 API，读取 `DASHSCOPE_API_KEY` 与可选的 `DASHSCOPE_BASE_URL`，将任务参考图作为 Base64 图像输入，并验证锚点哈希。三种模式均先确认首图锚点再生成余图，使用相同的图片审核和提升机制。失败时只能重试当前 provider，不得跨 provider 切换。

图片任务是业务规则唯一来源。执行者只可按原字段格式化请求，不能新增人物、物件、剧情、画面规则，不能把“允许”擅自收紧为“禁止”。`rule_manifest` 保存规则来源；`verify images` 会将任务包逐项与正式分镜重新构建出的规范任务比对，拒绝任何改写，以及缺图、非 16:9 图和高相似候选。普通场景可使用有助理解、少量且从属的画内文字，但底部中央字幕区禁止任何可读文字；同时禁止段落、密集 UI、字幕、乱码和水印。

首次生成的风格锚点与普通镜头都采用 `text_policy=useful_in_scene`：只允许自然属于场景、语义有用且视觉从属的少量文字、数字或货币符号，并继续禁止字幕、长段落、密集文字、乱码和水印。

万相返回的候选 PNG 可能带透明通道，而其参考图接口不接受透明通道。上传锚点时只在内存中将参考副本铺白并归一化为 RGB PNG，不改动已确认候选文件或其哈希。

正式图片路径统一为 `assets/scenes/{block_idx:02d}_{beat_idx}.png`。历史图片没有来源元数据时原样保留，不做伪造。

## 4. Azure、渲染与 QA

`script` 提升后 voice 与 storyboard 同时解锁，所以 Azure 配音可与分镜/图片分支并行：

```bash
$PY pipeline/workflow.py run <run_id> voice
$PY pipeline/workflow.py run <run_id> render
$PY pipeline/workflow.py run <run_id> qa
```

- Azure 音色来自 `project.json.providers.speech.voice`。
- 密钥/区域来自 `AZURE_SPEECH_KEY`、`AZURE_REGION` 或根 `.env`。
- 网络、429、5xx 错误在 Azure 内最多重试 3 次，退避 2/5/10 秒。
- 失败后状态为 `failed`，已完成的音频缓存与 run 保留；再次运行同一阶段恢复。
- 不存在 Piper、Edge、系统 TTS 或自动语音回退。

渲染只读取正式 `script.txt`、`storyboard.json`、`assets/scenes/` 和 Azure 缓存。图片缺失时公共层用程序化背景兜底，但不会调用其他图片模型。QA 使用 ffprobe 检查媒体规格，并执行完整解码。

## 5. 状态

统一状态为：`pending / awaiting_external / generated / verified / promoted / failed / blocked`。

- topic/copy/script/storyboard/images：`generated → verified → promoted`。
- voice/render/qa：运行成功后直接 `promoted`，不另设人工提升。
- 前置阶段未提升时保持 `blocked`。
- API 或外部生成失败标记 `failed`，可在同一 provider 内恢复。

随时检查：

```bash
$PY pipeline/workflow.py status <run_id>
```

## 6. 回归检查

```bash
$PY -m py_compile pipeline/*.py pipeline/providers/*.py
$PY -m unittest discover -s tests -v
$PY pipeline/build_long.py --project 001 --frames
$PY pipeline/build_long.py --project 002 --blocks 0,2,5 --no-tts
```

非连续块测试验证原块号到分镜/图片键的映射；抽帧用于字幕、缺图兜底与运镜检查。正式全片还需检查 1920×1080、音频响度、三段 BGM、SFX 与完整解码。

## 后置品牌与分发准备

品牌与发布准备是独立于 topic/copy/script/storyboard/images/voice/render/qa 的后置流程，不加入旧 run 的阶段状态。

品牌文件位于 `channels/{channel}/`，品牌候选和任务包位于该频道自己的候选与 workflow runs 目录。品牌必须恰好包含 5 个名称候选和 3 个视觉方向候选；人工选择后才能验证和提升。正式品牌固定频道定位“理解财富机制”、四个平台和“不作收益承诺”的内容政策。

发布初始化要求视频 run 的 QA 已 promoted、频道品牌已 promoted，并绑定该 run 当前 render revision。发布任务只读取正式 topic、copy、script、storyboard 和 brand，不调用图片、配音或渲染 provider。

发布包为 YouTube、B站、抖音、视频号各一套标题、两个备选标题、简介、标签和 CTA，并包含一套 16:9 封面任务。发布运行会从 `assets/scenes/` 按文件名选择最多三张正式常规 PNG（排除 `phase_*.png` 与候选素材）作为封面 style + character identity references；封面必须保持正式成片的画风、角色设定、比例、线条、色彩与光影，禁止不匹配的写实、极简或 3D 风格。验证会检查标题长度、封面短句、风格参考路径与 SHA-256、事实引用、脚本原文证据、源文件 hash 和收益承诺禁用词；没有正式常规场景时 publish-run 直接阻断。提升后写入 `publishing/releases/` 与 `upload.md`，上传前仍需人工检查封面与正式场景风格/角色一致性并人工上传。
